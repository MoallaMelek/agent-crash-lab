=== #11951 [open] 2026-10-30 by adtyavrdhn (MEMBER) comments=2 labels=
Harness Shell: continuing a conversation after a crash runs the interrupted command again
### Summary

If the process running an agent dies while a harness `Shell` command is running, and the conversation is then continued from its saved history, the command runs a second time.

The first run of the command does not die with the agent process. It keeps running in the workspace and finishes, so the resumed conversation does the same thing twice. For `git push`, `gh pr create` or a migration, that is a real problem.

### Steps

1. Run an agent with `DockerSandbox` (or `E2BSandbox`) and `Shell(tools=['shell'])`. The model calls `shell` with
   `echo "started $(date +%T)" >> /workspace/count; sleep 12; echo "finished $(date +%T)" >> /workspace/count`.
   Save `run.all_messages()` after every step of `agent.iter`.
2. Kill the process with `SIGKILL` while the command runs.
3. In a new process, load the saved history and call `agent.run(message_history=history, workspace=ref)`.

### What happens

```
before resume: ['started 09:39:04', 'finished 09:39:16']
after resume:  ['started 09:39:04', 'finished 09:39:16', 'started 09:39:19', 'finished 09:39:31']
```

The same happens on E2B.

### Why

`shell` and `start_command` name each job `sha256(f'{ctx.run_id}:{ctx.tool_call_id}')` (`shell/_toolset.py`, `_job_id`). The exclusive claim on that name is meant to stop a second launch of the same call. A resumed conversation is a new run with a new `run_id`, so the name changes and the command launches again.

Passing the old `run_id` does not help, because core refuses a `run_id` that already appears in `message_history`. Durable execution replays the `run_id`, so with DBOS `shell` ran once (`['started 10:25:37', 'finished 10:25:49']`, workflow `SUCCESS` after recovery).

### Suggested fix

Use the `run_id` of the `ModelResponse` that contains the tool call (found in `ctx.messages` by `tool_call_id`), and fall back to `ctx.run_id`. With that change, the resumed run attaches to the job that is already there and returns its result, and the command does not run again:

```
before resume: ['started 09:40:05', 'finished 09:40:17']
after resume:  ['started 09:40:05', 'finished 09:40:17']
```

# Capability hooks that touch external state cannot commit exactly once under durable execution

Capability hooks run in orchestration code on every durability engine, and orchestration code is
re-executed: replayed under Temporal, re-run on recovery under DBOS, re-run on flow retry under
Prefect. A capability whose hook writes to an external store therefore commits that write more than
once per model request, and there is no public API it can use to avoid it.

## Where the boundary actually sits

All three engines work the same way: the durability capability's `wrap_model_request` swaps
`request_context.model` for a `DurableModel` and calls `handler(request_context)`. The durable
dispatch happens inside `DurableModel.request` / `.request_stream`, which is *below* the whole
capability chain.

- `durable_exec/temporal/_durability.py` -- `TemporalDurability.wrap_model_request`
- `durable_exec/dbos/_durability.py` -- `DBOSDurability.wrap_model_request`
- `durable_exec/prefect/_durability.py` -- `PrefectDurability.wrap_model_request`
- `durable_exec/_utils.py` -- `DurableModel.request`

Ordering does not help. A capability listed after the durability capability in the `innermost` tier
nests inside its wrapper, but its body still runs on the calling side of the dispatch.

from `BaseDurabilityCapability._resolve_model_for_request` inside `request_activity` /
`_durable_model_scope`. Everything else -- `before_model_request`, `wrap_model_request`,
`after_model_request`, the tool hooks, the output hooks -- runs outside.
