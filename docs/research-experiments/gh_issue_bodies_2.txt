Simulated toolset: answer tool calls with a model, for evals and tests of agents whose tools have side effects
## Problem

Evaluating an agent end to end means letting it call its tools. For tools that send messages, charge cards, write to production systems or need credentials, that isn't an option in CI or in a `pydantic_evals` `Dataset` run. Today you can swap toolsets with `agent.override(toolsets=...)` and write a fake `FunctionToolset` by hand, but that means writing and maintaining a stub per tool and per scenario. Hand-written stubs usually return one canned value, so the agent never sees realistic variation (empty results, partial matches, errors), and multi-step flows break because the stubs don't stay consistent with each other (an order "created" in one call doesn't exist when the next call looks it up).

`TestModel` and `FunctionModel` cover the model side of a test. Nothing covers the tool side when you want plausible behavior without real execution.

A wrapper toolset that keeps the wrapped tools' definitions (names, descriptions, parameter schemas, return schemas) exactly as the agent sees them, but answers each call with a model instead of running it:

```python
simulated = SimulatedToolset(
    payments_toolset,
    model='openai:gpt-5-mini',
    scenario='The customer has two open orders; the second card on file is expired.',
    passthrough=['get_exchange_rate'],          # still executed for real
    fixtures={'get_customer': {'id': 'c_1', 'name': 'Ada'}},  # fixed answers
)

with agent.override(toolsets=[simulated]):
    result = await agent.run('Refund my last order')
```

=== #13781 [open] created=2026-11-17 updated=2026-11-17 by DouweM (CONTRIBUTOR) comments=0 labels=feature,area:durable-exec,pkg:core
Carry a durable unit's side effects (state changes, usage, events) back in its recorded output
> Written by Claude Code on behalf of @DouweM.

## Problem

Under durable execution, an activity's `RunContext` is a rebuilt copy: changes to it are lost, usage incurred inside it doesn't reach the parent run (#6886), and `ctx.emit()` / `ctx.enqueue()` raise inside the unit (#7971). There's no way for a tool running in an activity or step to send anything back to the workflow except its return value.

## Proposal

A durable unit records `(result, side_effects)`, where side effects are typed state operations, usage deltas and events. The workflow applies them in tool-call order, so replay applies the same effects in the same order from the recorded output.

- **Temporal:** carried in the activity result.
- **DBOS / Prefect:** carried in the step or task output (this also fixes the divergence between a cache hit and a fresh run).
- **AWS Lambda durable functions:** carried in the step result.

This extends #7971 (which covers events and queued messages) to state and usage, gives #6886 its transport, and is the foundation for a shared-state capability (#13782).

Rough size: M. Related: #7971, #6886.

Carry a durable unit's emitted events and enqueued messages in its recorded output
Under durable execution, `ctx.emit()` and `ctx.enqueue()` are side effects of *running* a durable unit rather than part of its recorded result, so they don't survive replay:

- **Prefect / DBOS**: `emit` works, and the event is delivered when the unit runs. On a flow retry, a cache hit, or DBOS recovery the recorded result is replayed without re-running the body, so the event is never re-emitted. Pinned by `test_prefect_task_wrapped_tool_emit_is_not_replayed`.
- **Temporal**: `emit` from a tool or event stream handler raises, because the activity's rebuilt `RunContext` has no path back to the run's event stream at all.
- **`ctx.enqueue()`**: rejected on all three engines by `EnqueueGuard` / `deserialize_run_context`, for the same reason — the enqueued messages would be dropped on replay, and unlike a missed event that changes what the model sees.

The consequence that matters: a capability cannot emit from its own tools under durable execution. `FileSystem` emitting a `FileReadEvent` from its read tool — the pattern `RepoContext` subscribes to — is lossy on Prefect/DBOS and a hard `UserError` on Temporal.
